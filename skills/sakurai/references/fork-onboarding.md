# 即プレイを妨げない任意の説明ページ設計（フォーク独自の拡張指針）

> このファイルはこのフォーク独自の拡張指針です。桜井氏が提唱した原則ではありません。原典由来の部分は動画番号（#017 など）を付け、独自解釈は【独自】と明記します。原典由来の記述は `planning.md`・`specs.md`・`ui.md` に実在する要点の範囲にとどめます。

桜井政博のゲーム作るには、の字幕から作った要点を土台にした、このフォーク独自の追加指針。番号は動画の通し番号（古い順）。

## 原則

- **説明は任意、プレイ開始は最短。深く知りたい人のための説明は別導線で提供する。**
- 初回起動で強制チュートリアルや長い説明を挟まない。ただし理解に不可欠な操作案内は例外とする。タイトル／メイン画面から、極力少ない操作で開始できるようにする。
- 「遊び方」「?」など、見つけやすい任意の説明導線を置く。説明を閉じたら、直前の画面・プレイ状態に戻れるようにする。
- ルールが直感的に伝わるUI・フィードバックを優先し、説明ページがないと遊べない設計にしない。規模・複雑さに合わせて適用し、説明ページの追加自体を無条件に義務化しない。

## なぜこうするのか（原典由来）

- ゲームは最初の3分で面白さが伝わるようにする。長いオープニングやプロローグ、スロースタートは損。前置きより先に本編を遊ばせる（#017）。プレイヤーは「まず操作したい」ので、導入はいきなり見せ場から始め、早く操作させる（#233）。
- 悪いチュートリアルは長文の説明書と、何もない練習場で操作させるもの。能動的に遊ばせながら学ばせるのが良く、操作が複雑なほど理解のための仕組みを企画に入れておく（#171）。練習場より、いきなり実戦に入れて戦いながら学ばせる方が、早く遊びたい気持ちにも盛り上がりにも合う（#085）。
- 初めて触れる人には最初の敷居を下げるが、手取り足取り導きすぎると冷める。ほどほどの自由度と、自分から入っていく演出も必要（#240）。
- プレイ時間はプレイヤーにとってコスト。ゲームは始めるまでの障壁が大きいので、それを上回る魅力が要る（#248）。
- 今時は長い導入説明をせず、先にゲームを始めさせる。ミッション説明もプレイ中に受けさせる（#113）。

## 二層導線の設計

- プレイヤーを「すぐ遊びたい人」と「詳しく学びたい人」の2層に分け、同じ画面から両方に届くようにする。すぐ遊びたい人の導線を既定（最短）にし、詳しく学びたい人の導線は任意で開く形にする。【独自】
- 原典の「前置きより先に本編」「能動的に遊ばせながら学ばせる」を、説明ページの置き場所として具体化したものと位置づける。【独自】

| 観点 | すぐ遊びたい人 | 詳しく学びたい人 |
|---|---|---|
| 入口 | タイトル／メイン画面の開始ボタン | 「遊び方」「?」など任意の導線 |
| 初回起動 | そのままプレイ開始 | 必要なときだけ説明を開く |
| 説明の量 | 1行ヒント程度 | 基本ルール → 操作 → 具体例 → コツ |
| 中断 | なし | ポーズから開き、閉じれば元に戻る |
| 前提 | 説明を読まなくても遊べる | 読みたい人が読める |

## 初回プレイまでの手数を増やさないパターン【独自】

- タイトル画面の隅に「?」を置き、開始ボタンは1つに保つ。開始の動線に説明を割り込ませない。
- 説明は別画面で開き、閉じると元の画面に戻る形にする。タイトルから開いたらタイトルへ、プレイ中に開いたらプレイへ戻す。
- プレイ中はポーズメニューから開けるようにし、プレイを止めた場所から再開できるようにする。
- 初回だけ1行ヒントを出し、詳しい説明へは任意で誘導する。ヒントは数秒で消えるか、閉じられるようにする。
- トップメニューからボタン連打だけで本編に入れるようにしておく（#238）。任意の説明導線と両立させる。
- 説明導線は見つけやすい位置に置くが、開始より目立たせない。重要度に応じて大きさを変える考え方（#145）を「?」の置き方にも当てはめる。
- 具体的なゲーム名やその仕様は前提にせず、一般化した設計パターンとして扱う。

## 説明に書く内容の段階

- 段階1: 基本ルール。何をすれば進むか、何が終わりか、勝ち負けや失敗の条件。
- 段階2: 操作。何を押すと何が起きるか。理解に不可欠な操作案内はここに置く。
- 段階3: 具体例。実際の場面でどうなるかを短く示す。
- 段階4: 攻略のコツ・学習事項。上達したい人向けの内容を最後に置く。
- 段階を分ける理由は、読む量を読む側に選ばせられること。全部を読ませず、必要十分な段階で止められるようにする。【独自】
- 操作が複雑なほど理解のための仕組みを企画に入れておく（#171）。段階分けはその仕組みの一つとして使う。
- 手取り足取り導きすぎると冷めるので、段階4は「読まなくても遊べる」位置づけにする（#240）。
- 説明文はメニュー項目名と同じ言葉で説明しない。専門用語を避け、ひらがなを開く（#227）。

## プレイ中の参照（中断負担の最小化）

- ポーズメニューから説明を開けるようにし、閉じたら元のプレイ状態に戻す。進行を巻き戻さず、リスタートもさせない。
- ゲームをしていない場面は必ずスキップできるようにする（#178）。説明画面も同じ扱いで、開いたらすぐ閉じられるようにする。
- プレイヤーは字幕を速く読む。セリフ単位で飛ばせる機能を付ける（#209）。説明も1ページ単位で送れるようにし、読み終わるまで待たせない。
- 参照中にゲームが止まるか止まらないかを画面上で明示し、開閉の操作を1つにまとめて元の画面へ戻る道を迷わせない。【独自】
- 参照した内容がプレイに反映される場合（設定の変更など）は、変更結果を確認できるようにする（#055）。

## やってはいけないこと（アンチパターン）

- 初回起動で強制チュートリアルを挟む。開始前に長文の説明を読ませる。説明を読まないと遊べない設計にする。
- 説明ページの追加を無条件に義務化する。小規模なゲームにまで段階的な説明を要求しない。
- 押しても反応しない導線を作る（#104）。「?」を置くなら、押したら必ず何かが起きるようにする。
- 説明を閉じたあと、元の画面・状態に戻らない。説明を開くまでに複数の階層をたどらせる。【独自】
- ルールをUIやフィードバックで伝えず、文章だけに逃がす。【独自】

## 適用の判断（規模・複雑さに合わせる）

- 小規模（ルールが1〜2個）なら、1画面の「遊び方」で足りる。段階を分けない。中規模なら「基本ルール＋操作」と「コツ」の2段階に分ける。
- 複雑（操作やリソースが多い）なら段階を増やし、プレイ中の参照も用意する。規模が大きい作品では、説明や設定を手厚くしてよい（#055）。
- 説明がなくても遊べるUIを優先する。説明は補助として置く。
- 分かりやすいUIとスタイリッシュなUIは相反しやすい。ゲームごとに目的に合わせてどちらを優先するか決める（#018）。
- 常時出すとうるさい物は状況で出し入れする（#252）。ヒント表示も同じ扱いにする。

## 新規作成時のチェックリスト

- 初回起動から、説明を読まずにプレイを開始できるか。タイトル／メイン画面から開始までの操作が最短になっているか。
- 「遊び方」「?」など任意の説明導線が見つけやすい位置にあり、開始の動線を邪魔していないか。
- 説明を閉じたとき、開く前の画面・プレイ状態に戻るか。
- 説明が基本ルール → 操作 → 具体例 → コツの順に段階分けされているか。
- 説明を読まなくても、UIとフィードバックだけでルールが伝わるか。
- 押せる導線がすべて何らかの反応を返すか（#104）。
- 規模に見合った説明量か。義務的に段階を増やしていないか。

## レビュー時のチェックリスト

- 開始前に強制チュートリアルや長文説明が挟まっていないか。説明ページがないと遊べない箇所がないか。
- 説明の入口が開始の動線を邪魔していないか。
- 説明を閉じたあと元の状態に戻るか。巻き戻りやリスタートが起きていないか。
- プレイ中の参照がポーズから開け、中断負担が小さく済むか。
- 説明文が専門用語だらけになっていないか。メニューの言葉の言い換えになっていないか（#227）。
- 説明画面をすぐ閉じられるか。読み終わるまで待たされないか（#178 #209）。
- 説明の段階が規模に対して過剰、または不足していないか。
